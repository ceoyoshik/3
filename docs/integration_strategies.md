# Сравнительный анализ стратегий интеграции

## 1. Кратко о стратегиях

| Стратегия | Суть | Что нужно для тестирования |
| --- | --- | --- |
| Нисходящая | сверху вниз: сначала верхние модули | заглушки (stubs) для нижних |
| Восходящая | снизу вверх: сначала нижние модули | драйверы (drivers) для верхних |
| Сэндвич | верхние и нижние, затем средние | и заглушки, и драйверы |
| Риск-ориентированная | первыми — самые рискованные модули | драйверы и заглушки по шагам |
| Функционально-ориентированная | по функциям системы, а не по модулям | сквозные сценарии |
| Т-образная | сначала вертикальный слой через всю систему | минимальные реализации остальных частей |

## 2. Преимущества и недостатки

| Стратегия | Преимущества | Недостатки |
| --- | --- | --- |
| Нисходящая | рано виден общий каркас и интерфейсы; удобна для демонстрации | нижние модули проверяются поздно; много заглушек |
| Восходящая | нижние (часто самые важные) модули проверяются рано; заглушки не нужны | система целиком появляется в самом конце; нужны драйверы |
| Сэндвич | параллельная работа двух команд; раннее обнаружение ошибок с двух сторон | сложнее планировать; нужны и заглушки, и драйверы |
| Риск-ориентированная | самые опасные ошибки находятся первыми; ресурсы идут туда, где они нужнее | требует оценки рисков; порядок не совпадает со структурой системы |
| Функционально-ориентированная | результат ценен для пользователя уже после каждой функции | модули могут затрагиваться многократно; сложнее отследить покрытие |
| Т-образная | быстро проверяется вся архитектура «насквозь» | остальные слои долго остаются «тонкими»; риск переделок |

## 3. Рекомендации по выбору

| Тип проекта | Рекомендуемая стратегия | Почему |
| --- | --- | --- |
| Небольшая программа с одним сложным алгоритмом (как «МатрСум-11») | риск-ориентированная | основной риск сосредоточен в одном модуле и канале обмена |
| Система с готовой архитектурой и устойчивыми интерфейсами | нисходящая | интерфейсы известны заранее, нижние слои реализуются позже |
| Библиотеки, драйверы, вычислительные ядра | восходящая | надёжность нижнего уровня важнее интерфейса |
| Большие системы с несколькими командами | сэндвич | команды работают навстречу друг другу |
| Веб-сервисы и продукты с частыми релизами | функционально-ориентированная | каждая функция сразу доступна пользователю |
| Новая архитектура, нужно проверить её жизнеспособность | Т-образная | один сквозной сценарий проверяет все слои |

## 4. Почему для проекта выбрана риск-ориентированная стратегия

1. Проект содержит три небольших модуля, но риск распределён неравномерно:
   ошибка в обработке (сравнение вещественных с нулём, суммирование) делает
   неверным весь результат.
2. Канал обмена (отдельный процесс и JSON-файлы) — единственное место,
   где возможны недоступность, тайм-аут и конфликт версий, поэтому его
   проверяют сразу после обработки.
3. Модуль вывода прост, его подключают последним, пока он заменён заглушкой.
4. Нисходящая стратегия отложила бы проверку обработки до конца, восходящая —
   не дала бы заранее проверить канал обмена, поэтому порядок определяется
   рисками, а не структурой.
